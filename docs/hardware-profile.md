# Паспорт железа

**Снят на целевом устройстве 2026-09-12.** Единственный источник бюджетов и допущений о железе
в этом проекте. Числа из исследований и чужих статей сюда не попадают (PRACTICES §3.1).

Сырой вывод прибора — `docs/measurements/2026-09-12-quest3-raw.md` (137 расширений устройства).

## Достоверность

В паспорте сведены **три прогона**. Ниже — итоговый, с исправленным прибором и XR-вьюпортом;
именно он считается основным:

```
passed=39 failed=2 unknown=0     пол: исполнено 41/41 проверок
PASS  контроль vk: VK_KHR_swapchain           — прибор видит расширения устройства
PASS  контроль xr: XR_KHR_vulkan_enable2      — прибор видит расширения рантайма
PASS  фальсификатор vk: несуществующее имя → ABSENT
PASS  фальсификатор xr: несуществующее имя → ABSENT
```

Оба контрольных случая и оба фальсификатора зелёные, пол сошёлся. Значит **двум отказам можно
верить**: это факты о железе, а не слепота прибора.

История прогонов, чтобы числа не путались:

| Прогон | Что мерил | Вердикт |
|---|---|---|
| 1-й (14:42) | только расширения, **без XR-вьюпорта** | 17/2, пол 19/19 |
| 2-й (15:36) | + нагрузка, 18 минут; прибор ещё врал про вердикты движка | 40/4, **пол 44/45 — не сошёлся** |
| 3-й (16:27) | исправленный прибор, фаза E пропущена | 39/2, пол 41/41 |
| 4-й (17:47) | полный: + опрос частот и проверка дрейфа, 18 минут | **45/2, пол 47/47** |

Числа под нагрузкой (draw call, разогрев, троттлинг) взяты из 2-го прогона — он единственный
прошёл 18 минут; они подтверждены 3-м в третьем знаке по CPU. Вердикты движка и расширения — из
3-го: во 2-м прибор спрашивал не тот слой и ложно докладывал, что multiview отключён.

## Vulkan

| Поле | Значение |
|---|---|
| Версия API | **1.3.295** |
| Расширений устройства | 137 |
| `XrGraphicsRequirementsVulkan2KHR` | min 1.0.0, **max 1.2.0** |

**Vulkan 1.4 на этом железе нет.** Исследование трижды закладывалось на 1.4 — это опровергнуто.

Отдельная странность, которую стоит держать в уме: рантайм заявляет `maxApiVersionSupported: 1.2.0`,
при этом Godot фактически работает на 1.3.295. Расхождение не объяснено, на работу не влияет.

### Расширения, от которых зависели архитектурные решения

| Расширение | Есть? | Следствие |
|---|---|---|
| `VK_KHR_multiview` | **да** | стерео одним проходом доступно |
| `VK_KHR_dynamic_rendering` | **да** | |
| `VK_KHR_dynamic_rendering_local_read` | **НЕТ** | вошло в core только в 1.4; драйвер не экспортирует. Ветка исследования «тайловая постобработка через local_read» на этом железе неосуществима |
| `VK_KHR_create_renderpass2` | **да** | остаётся классический путь с subpasses — тот, от которого исследование отговаривало |
| фовеация | **да** | `VK_EXT_fragment_density_map`, `VK_EXT_fragment_density_map2`, `VK_KHR_fragment_shading_rate` — доступны оба семейства |

### Чего исследование не заметило: вендорский тайловый набор

Документ поставил на отсутствующее расширение, пройдя мимо девяти QCOM-расширений, которые
на этом железе **есть** и закрывают ту же задачу:

| Расширение | Зачем |
|---|---|
| `VK_QCOM_tile_properties` | запросить фактические размеры тайла — вместо догадок про «16×16» из исследования |
| `VK_QCOM_render_pass_store_ops` | расширенные store-операции; та же экономия пропускной способности, что обещал `local_read` |
| `VK_EXT_load_store_op_none` | `loadOp`/`storeOp` = NONE |
| `VK_QCOM_render_pass_shader_resolve` | resolve прямо на тайле |
| `VK_QCOM_multiview_per_view_viewports` | **настоящий** аналог того, что исследование назвало `VK_NVX_multiview_per_view_attributes` (вендорское имя NVIDIA, на Adreno отсутствует) |
| `VK_QCOM_multiview_per_view_render_areas` | то же для областей рендера |
| `VK_QCOM_fragment_density_map_offset` | сдвиг области фовеации |
| `VK_QCOM_render_pass_transform` | пре-ротация без лишнего blit |
| `VK_EXT_astc_decode_mode` | ASTC |

**Вывод не «тайловая стратегия невозможна», а «она достигается другим, вендорским путём».**
Проработка этого пути — предмет ADR-0003 (рендер-путь), который теперь можно писать по числам.

а в пресете экспорта стоит `xr_features/passthrough=0`. Не проверено — отдельный прогон с
включённым passthrough это либо подтвердит, либо снимет.

# Измерения под нагрузкой — 2026-09-12

Прогон с XR-вьюпортом, то есть с настоящим рендером в шлем. Предыдущий прогон шёл **без** него
(`No viewport was marked with use_xr`) и мерил только возможности.

Сырые данные: `docs/measurements/2026-09-12-quest3-measured-raw.md`,
`docs/measurements/2026-09-12-quest3-sustained-18min.tsv` (1080 выборок).

## Кадровый бюджет

| Поле | Значение |
|---|---|
| Частота обновления | **72.0 Гц** |
| Кадровый бюджет | **13.89 мс** |

**Godot не запрашивает 90 Гц**, хотя `XR_FB_display_refresh_rate` на устройстве доступен. Бюджет,
в котором проект живёт по умолчанию, — 13.89 мс, а не 11.1 мс из исследования.

## Стоимость отрисовки

Два независимых прогона, второй — с исправленным прибором (он и считается основным):

| Метрика | CPU | GPU |
|---|---|---|
| Один draw call (небатченый) | **1.04–1.05 мкс** | **5.05–5.34 мкс** |
| Один инстанс (MultiMesh) | **0.019 мкс** | **0.082 мкс** |

Совпадение двух прогонов в третьем знаке по CPU и в пределах 6% по GPU — сам по себе довод в
пользу достоверности: это разброс между прогонами, а не между правками (PRACTICES §3.5).

Свип `N = 0 … 1600`, крошечные квады (0.01 м) — филлрейт не мерялся:

```
небатченый:  N=0    calls=0     CPU 0.104  GPU 2.432
             N=400  calls=400   CPU 0.460  GPU 3.998
             N=1600 calls=1600  CPU 1.767  GPU 10.507
инстансы:    N=1600 calls=1     CPU 0.133  GPU 2.918
```

### Главное следствие: в отрисовке связывает GPU, а не CPU

Исследование утверждало (стр. 8): «Центральный процессор становится главным узким местом
системы». **Для отрисовки это неверно.** При 1600 вызовах CPU занял 1.77 мс, а GPU — 10.51 мс
из 13.89. Draw call стоит GPU **в пять раз дороже**, чем CPU. Даже пустая сцена с XR-вьюпортом
стоит GPU 2.4 мс при 0.1 мс CPU.

**Границы вывода.** Измерялась только подача геометрии. Физика, игровая логика и ИИ не
измерялись — для них посылка исследования про CPU может оказаться верной. Утверждение этого
паспорта: в **отрисовке** связывает GPU.

Квады крошечные, значит это не филлрейт, а цена подачи геометрии и биннинга на тайловой
архитектуре. Вывод для движка: агрессивный батчинг нужен не «чтобы разгрузить CPU», как писал
документ, а чтобы разгрузить **GPU**, и выигрыш там впятеро больше ожидаемого.

Инстансинг даёт **1 вызов отрисовки на 1600 объектов** и обходится в 55 раз дешевле по CPU.

### Разогрев PSO

Пик первых 30 кадров после появления новых материалов — **на 3.59 мс выше** установившегося
(3.81 против 0.22 мс). Это четверть кадрового бюджета: предупреждение исследования про
микрофризы на компиляции шейдеров подтверждено числом.

### Достоверность свипов

| Защита | Результат |
|---|---|
| Гейт: ΔN → Δdraw calls | 1600 → 1600, **1.00 на объект** — случай задевает гейт |
| Гейт инстансов | ΔN=1600 → Δcalls=1 — режимы различаются |
| Нулевая точка | 0.104 мс, меньше половины бюджета |
| Разброс двух прогонов на N=100 | **0.004 мс** против шага свипа 1.663 мс — в 400 раз ниже шума |
| Частота во время свипов | устойчива 72.0 Гц, свипы не аннулированы |

**Оговорка:** на точке N=800 счётчик движка показал **658** вызовов вместо 800. Гейт проверял
только концы свипа и этого не поймал. Наклон считался по концам (0 и 1600), где расхождения нет,
но точка N=800 в отчёте недостоверна. Проверка по всем точкам добавлена после этого прогона.

## Вердикты движка

Не путать с доступностью расширений: это то, что Godot **включил и станет использовать**.

| Фича | Вердикт |
|---|---|
| `SUPPORTS_MULTIVIEW` | **включено** — стерео одним проходом работает |
| `SUPPORTS_ATTACHMENT_VRS` | **включено** — фовеация через attachment доступна |
| `SUPPORTS_FRAMEBUFFER_DEPTH_RESOLVE` | **включено** — resolve глубины на тайле |
| `SUPPORTS_HALF_FLOAT`, `VULKAN_MEMORY_MODEL`, `BUFFER_DEVICE_ADDRESS`, `IMAGE_ATOMIC_32_BIT`, `POINT_SIZE`, `HDR_OUTPUT` | включено |
| `SUPPORTS_RAY_QUERY`, `SUPPORTS_RAYTRACING_PIPELINE` | не включено |

Аппаратная трассировка лучей у Adreno 740 есть, но Godot её на этой платформе не включает.

**Предостережение на будущее.** Первая версия прибора доложила, что `SUPPORTS_MULTIVIEW` и
`SUPPORTS_ATTACHMENT_VRS` **не включены** — и это было ложью. Запрос уходил драйверу
(`RenderingDeviceDriverVulkan::has_feature`), у которого `default: return false` и который эти
две фичи не обрабатывает вовсе; их перехватывает слой выше, `RenderingDevice::has_feature`
(`rendering_device.cpp:9035-9049`). Спрашивать надо `RenderingDevice`.

| Поле | Значение |
|---|---|

| Нагрузка | N=1600, ~77% бюджета по GPU |

| CPU за прогон | сред 1.632, мед 1.637, p95 1.770, макс 2.300 мс |
| GPU за прогон | сред 10.593, мед 10.648, p95 **11.169**, макс 11.448 мс |
| Смена частоты | **не зафиксирована ни разу** |

### Доступные частоты: 90 Гц ЕСТЬ, Godot их не запрашивает

Опрошено прибором на устройстве:

```
доступные частоты: [72.0, 80.0, 90.0, 120.0]
```

Два следствия.

**Первое: бюджет 11.1 мс достижим.** Исследование считало от 90 Гц, и 90 Гц устройство даёт.
Godot по умолчанию работает на 72 Гц и выше не запрашивает, хотя `XR_FB_display_refresh_rate`
доступен. Это управляемый параметр, а не ограничение железа.

**Второе: проверка троттлинга по смене частоты была пустой.** 72 Гц — самая низкая из доступных,
сбрасывать было некуда. Прибор теперь говорит это сам:

```
PASS  запас вниз: прогон идёт на САМОЙ НИЗКОЙ доступной частоте 72.0 Гц —
      слежение за сменой частоты почти ничего не покажет
```

Ранее эта предпосылка была взята из исходного исследования и не проверена. Теперь измерена.

### Настоящий сигнал: дрейф времени кадра

При троттлинге тактовых частот та же нагрузка стала бы считаться дольше. Два прогона по 18 минут:

| Прогон | Четверти, GPU сред, мс | Худшая к первой | Конец к началу |
|---|---|---|---|
| 15:36 | 10.672 → 10.590 → 10.656 → 10.691 | +0.2% | +0.2% |
| 18:05 | 10.588 → 10.991 → 11.047 → 10.817 | **+4.3%** | +2.2% |

**Форма важнее числа.** По минутам второй прогон даёт не ровную линию, а горб: рост с 10.50 до
~11.12 за первые семь минут (+6%), плато до 14-й минуты, затем спад до 10.56–10.82.

```
мин  0: 10.500   мин  6: 10.910   мин 12: 11.069
мин  1: 10.785   мин  7: 11.113   мин 13: 11.066
мин  2: 10.986   мин  8: 11.010   мин 14: 11.119
мин  3: 10.009   мин  9: 11.117   мин 15: 10.557
мин  4: 10.872   мин 10: 10.945   мин 16: 10.824
мин  5: 10.896   мин 11: 11.045   мин 17: 10.641
```

Выборок 59–60 в минуту, то есть форма не артефакт неравномерности.

**Вывод: устойчивого троттлинга нет.** Есть разогрев ~6% за первые семь минут с последующей
стабилизацией — это не деградация, а выход на рабочий режим. Спад в конце прогона деградации
прямо противоречит.

**Чего этот вывод НЕ покрывает** (PRACTICES §3.2): более плотную нагрузку, работу на 90 Гц (где
бюджет 11.1 мс и запас впятеро меньше) и прогоны дольше 18 минут. На 90 Гц результат может быть
совершенно другим — там ОС уже сможет сбросить частоту, и проверка по частоте перестанет быть
пустой.

**Оговорка о самой метрике.** Первая версия сравнивала последнюю четверть с первой и дала +2.2%,
горба не увидев: её вердикт зависел от того, где прогон случайно закончился (обрыв на 14-й минуте
дал бы +3.3%). Исправлено на сравнение **худшей** четверти с первой — она отвечает на вопрос
«становилось ли хуже», а не «хуже ли стало к концу». Порог 5% назначен по двум прогонам, а не
выведен из природы явления, и при +4.3% запас до него **невелик**. Проверка ни разу не краснела,
то есть её различающая способность не подтверждена (PRACTICES §2.4).

**Оговорка:** 9 выборок из 1080 (0.8%) показали ноль вызовов отрисовки и время на уровне пустой
сцены — секунды 20, 280, 284, 1014, 1016, 1019–1021. Сцена на мгновение не рендерилась. Причина
**не установлена**. Эти выборки вошли в общую статистику и слегка занижают средние.

## Что ещё выяснилось на устройстве

- **Swappy принудительно отключается под OpenXR.** В логе: `VulkanHooks detected (e.g. OpenXR):
  Force-disabling Swappy Frame Pacing.` Кадровым пейсингом в VR занимается композитор шлема.
  Для VR-пути Swappy не решает ничего. ADR-0004 **уже исправлен**: флаг `swappy=yes` оставлен,
  но обоснование переписано — он защищает не-XR сборки, а не VR.
- **`rendering_method.mobile="mobile"` обязателен.** Без платформенного оверрайда навязывается
  `forward_plus`, что на шлеме даёт `Forward Mobile` не увидеть вовсе.
- **`xr/shaders/enabled=true` обязателен в `project.godot`.** Без него обход issue #115924
  не срабатывает и Vulkan-устройство вообще не создаётся.

## Что НЕ измерено

- **Реальный размер тайла.** `VK_QCOM_tile_properties` на устройстве есть, но Godot не включает
  расширение при создании устройства, а список захардкожен в приватном методе
  (`rendering_device_driver_vulkan.cpp:557-571`). Нужен патч внутрь `godot/` — по ADR-0002
  требует отдельного ADR. Отложено решением владельца.
- **Экономия от MSAA с `LAZILY_ALLOCATED`.** Требует GPU-счётчиков, недоступных отсюда.
- **Поведение на 90 Гц.** Все измерения сделаны на 72 Гц; запрос более высокой частоты через
  `XR_FB_display_refresh_rate` не пробовался.
- **Работа на 90 Гц.** Устройство их предлагает (измерено), но ни один прогон на них не делался.
  Там бюджет 11.1 мс — запас впятеро меньше, и выводы про draw calls и троттлинг нужно
  перепроверять заново.
- **Троттлинг за пределами 18 минут** и под более плотной нагрузкой.
- **Точка N=800** в свипе недостоверна (счётчик движка 658 вместо 800).
- **Причина девяти пустых выборок** в длинном прогоне.
- **Филлрейт.** Мерились крошечные квады — цена пикселей намеренно исключена.
- **Проверка гейта по всем точкам не была испытана в красном.** Она добавлена после того, как на
  N=800 счётчик показал 658, но в проверочном прогоне расхождений не возникло и строка не
  напечаталась. Непрогнанная в отказ проверка ничего не доказывает (PRACTICES §2.4).

## Когда обновлять этот файл

- Обновилась Horizon OS, драйвер Adreno или версия рантайма Oculus — **перемерить**, старое
  перенести в раздел истории.
- Прибор получил новую проверку — добавить строку и перегнать.
- Прогон с включённым passthrough — закрыть вопрос про `XR_META_environment_depth`.
- Любое число отсюда попало в код — убедиться, что оно всё ещё актуально.
- Сменилась версия Godot: `rendering_method`, обход #115924 и поведение Swappy могли измениться.
