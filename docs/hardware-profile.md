## Достоверность

В паспорте сведены **три прогона**. Ниже — итоговый, с исправленным прибором и XR-вьюпортом;
именно он считается основным:

```
passed=39 failed=2 unknown=0     пол: исполнено 41/41 проверок
PASS  контроль vk: VK_KHR_swapchain           — прибор видит расширения устройства
PASS  контроль xr: XR_KHR_vulkan_enable2      — прибор видит расширения рантайма
PASS  фальсификатор vk: несуществующее имя → ABSENT
PASS  фальсификатор xr: несуществующее имя → ABSENT
```

### Чего исследование не заметило: вендорский тайловый набор

Документ поставил на отсутствующее расширение, пройдя мимо девяти QCOM-расширений, которые
на этом железе **есть** и закрывают ту же задачу:

| Расширение | Зачем |
|---|---|
| `VK_QCOM_tile_properties` | запросить фактические размеры тайла — вместо догадок про «16×16» из исследования |
| `VK_QCOM_render_pass_store_ops` | расширенные store-операции; та же экономия пропускной способности, что обещал `local_read` |
| `VK_EXT_load_store_op_none` | `loadOp`/`storeOp` = NONE |
| `VK_QCOM_render_pass_shader_resolve` | resolve прямо на тайле |
| `VK_QCOM_multiview_per_view_viewports` | **настоящий** аналог того, что исследование назвало `VK_NVX_multiview_per_view_attributes` (вендорское имя NVIDIA, на Adreno отсутствует) |
| `VK_QCOM_multiview_per_view_render_areas` | то же для областей рендера |
| `VK_QCOM_fragment_density_map_offset` | сдвиг области фовеации |
| `VK_QCOM_render_pass_transform` | пре-ротация без лишнего blit |
| `VK_EXT_astc_decode_mode` | ASTC |

**Вывод не «тайловая стратегия невозможна», а «она достигается другим, вендорским путём».**
Проработка этого пути — предмет ADR-0003 (рендер-путь), который теперь можно писать по числам.

### Свойства системы OpenXR (5-й прогон)

| Поле | Значение |
|---|---|
| Система | `Meta Quest 3`, vendor `0x2833` |
| **Лимит composition layers** | **32** |
| Максимальный swapchain | 8192 × 8192 |
| Отслеживание ориентации / позиции | да / да |

**Лимит в 32 слоя закрывает один из вариантов шар-меню.** В дорожной карте этап 1 требует, чтобы
человек находил нужный пункт из **40+**. Значит отдельный composition layer на ячейку
невозможен: шар обязан быть одним слоем с нарисованной текстурой либо сеткой в мировом буфере.
Это вход в ADR-0003 и в этап 1.

Спрошено у рантайма через `xrGetSystemProperties`, вызванную по `get_instance_proc_addr()`:
прямой вызов не линкуется, символ наружу из модуля `openxr` не экспортируется.

Отсутствие `XR_META_environment_depth` означает, что раздел исследования про динамическое
перекрытие в MR (Depth API, depth keying) на текущей конфигурации нереализуем.

**Причина не установлена.** Правдоподобная гипотеза: расширение может быть завязано на passthrough,
а в пресете экспорта стоит `xr_features/passthrough=0`. Не проверено — отдельный прогон с
включённым passthrough это либо подтвердит, либо снимет.

## Стоимость отрисовки — на 72 Гц

**Все числа этого раздела относятся к 72 Гц.** На 120 Гц они другие — см. «Числа зависят от
частоты» ниже. Переносить их между частотами нельзя (ADR-0006, правило 4).

Два независимых прогона, второй — с исправленным прибором (он и считается основным):

| Метрика | CPU | GPU |
|---|---|---|
| Один draw call (небатченый) | **1.04–1.05 мкс** | **5.05–5.34 мкс** |
| Один инстанс (MultiMesh) | **0.019 мкс** | **0.082 мкс** |

Совпадение двух прогонов в третьем знаке по CPU и в пределах 6% по GPU — сам по себе довод в
пользу достоверности: это разброс между прогонами, а не между правками (PRACTICES §3.5).

Свип `N = 0 … 1600`, крошечные квады (0.01 м) — филлрейт не мерялся:

```
небатченый:  N=0    calls=0     CPU 0.104  GPU 2.432
             N=400  calls=400   CPU 0.460  GPU 3.998
             N=1600 calls=1600  CPU 1.767  GPU 10.507
инстансы:    N=1600 calls=1     CPU 0.133  GPU 2.918
```

### Главное следствие: в отрисовке связывает GPU, а не CPU

Исследование утверждало (стр. 8): «Центральный процессор становится главным узким местом
системы». **Для отрисовки это неверно.** При 1600 вызовах CPU занял 1.77 мс, а GPU — 10.51 мс
из 13.89. Draw call стоит GPU **в пять раз дороже**, чем CPU. Даже пустая сцена с XR-вьюпортом
стоит GPU 2.4 мс при 0.1 мс CPU.

**Границы вывода.** Измерялась только подача геометрии. Физика, игровая логика и ИИ не
измерялись — для них посылка исследования про CPU может оказаться верной. Утверждение этого
паспорта: в **отрисовке** связывает GPU.

Квады крошечные, значит это не филлрейт, а цена подачи геометрии и биннинга на тайловой
архитектуре. Вывод для движка: агрессивный батчинг нужен не «чтобы разгрузить CPU», как писал
документ, а чтобы разгрузить **GPU**, и выигрыш там впятеро больше ожидаемого.

Инстансинг даёт **1 вызов отрисовки на 1600 объектов** и обходится в 55 раз дешевле по CPU.

## Целевая частота 90 Гц: измерено (прогон 9)

Первые числа на частоте, под которую проектируется движок (ADR-0007). Сняты чередующейся
матрицей 72 → 90 → 72 → 90 в одной сессии; счётчик отрисовок сошёлся с заявленным на всех
12 точках, то есть наклоны посчитаны по настоящей нагрузке.

| Метрика | 72 Гц (минимум) | 90 Гц (**цель**) |
|---|---|---|
| Бюджет кадра | 13.89 мс | **11.11 мс** |
| Один draw call, GPU | 4.961 мкс | **4.037 мкс** |
| Пустая сцена, GPU | 2.722 и 3.345 мс | **2.629 и 2.887 мс** |
| N=1600, GPU | 10.696 и 11.247 мс | **8.928 и 9.506 мс** |
| N=1600, CPU | 1.760 и 1.817 мс | 1.868 и 1.924 мс |
| Промахи по дедлайну | нет | **нет** |
| Клок GPU под нагрузкой | 456 МГц | 535 МГц |

**Нагрузка в 1600 объектов укладывается в целевой бюджет** с запасом 15–20% и без единого
промаха по дедлайну. Для сравнения, на 120 Гц та же нагрузка пробивала бюджет в 32–40% кадров.

### В рабочем диапазоне загадки нет: это разгон

Разница цены draw call между 72 и 90 Гц значима — 0.924 мкс против разброса внутри частоты
0.200, — и принадлежит частоте: ряд приращений пилообразный.

Но её объясняет клок:

```
клок:          456 → 535 МГц   отношение 1.174
цена вызова: 4.961 → 4.037 мкс отношение 1.229
остаток после нормировки:               1.047
```

Остаток 1.047 лежит в шуме. **Это принципиально отличается от пары 72↔120**, где тот же расчёт
оставлял необъяснёнными ≈1.5. Значит необъяснённая часть — свойство перехода к высоким частотам,
а не общее свойство частоты, и **внутри рабочего диапазона 72–90 Гц поведение предсказуемо**.

### Цена пикселя: измерена, от частоты не зависит

Свип по размеру квада при восьми слоях с выключенным тестом глубины; покрытие считается через
проекцию камеры с обрезкой по вьюпорту.

| Прогон | 72 Гц | 90 Гц | Отношение |
|---|---|---|---|
| 8-й | 135.1 мкс/Мпикс | 140.5 | 1.04 |
| 9-й | 119.4 мкс/Мпикс | 117.2 | 0.98 |

**Цена пикселя от частоты не зависит — воспроизведено дважды.** Абсолютное значение гуляет между
прогонами примерно на 15%, и это его текущая точность.

**Отсюда главный вывод о механизме:** цена вызова от частоты зависит, цена пикселя — нет. Значит
частотный эффект живёт в **подаче геометрии и биннинге**, а не в затенении. Пиксельные объяснения
(фовеация, разрешение, филлрейт) закрыты все.

### Дрейф за прогон

Канарейка — одинаковая нагрузка N=400 на каждой ступени — показала между повторами одной частоты
**+4.6% на 72 Гц и +13.1% на 90 Гц**; база пустой сцены за прогон тоже ползёт вверх. За сто
секунд условия действительно уезжают, и это ограничивает доверие к абсолютным числам примерно
этими процентами. Выводы о разнице между частотами это не отменяет: чередующийся порядок ступеней
сделан ровно для того, чтобы дрейф был отделим, и проверка принадлежности его отделила.

  больше в снимке не менялось ничего.
- **Разгон исключён.** Клок GPU все 48 секунд L1 держался на **456 МГц**, ни одного перехода.
- **Артефакт окна замера исключён независимым свидетелем.** Загрузка GPU с хоста
  (`gpu_busy_percentage`, включает и работу композитора) повторяет форму: **49–58% при off**
  в начале и в конце каждой сцены против **39–45% при 2x/4x** в середине. На 90 Гц десять
  пунктов ≈ 1.1 мс — тот же масштаб, что измерил прибор.
- Обкатка в быстром режиме показала то же направление дважды.

**Подпись эффекта: с MSAA цена вызова почти исчезает.** При 2x сцена из 400 вызовов стоит
3.194–3.231 мс, а сцена из 8 вызовов с полным затенением — 3.185–3.196. Без MSAA 400 вызовов
стоят на ≈1 мс дороже, чем 8 слоёв пикселей.

**Механизм не установлен.** В `render_forward_mobile.cpp` ветка MSAA выбирает другие вложения,
но причины удешевления там не видно. Гипотеза, не проверенная и в выводы не взятая: MSAA
удерживает драйвер Adreno в тайловом режиме (GMEM), а без него драйвер выбирает прямой режим,
где подача геометрии дороже. Это та же версия, что висит над аномалией 72↔120 Гц.

**Главное следствие: все числа стоимости отрисовки в этом паспорте сняты при MSAA off.** Если
проект включает 2x, цену вызова и базу пустой сцены надо перемерить под 2x — формула бюджета из
ADR-0003 на прежних числах для 2x недействительна. → Перемерено прогоном 11, см. ниже.

**Поправка прогона 11 к подписи.** «С MSAA цена вызова почти исчезает» — **неверно**. Лестница
показала, что при 2x вызов стоит столько же на концах и дешевле посередине; см. следующий раздел.

## Форма кривой вызовов и стадии рендера (прогон 19, 90 Гц, 2026-09-14)

Фаза K: 18 точек 0…1600 × MSAA off/2x × проход вверх и вниз (ABBA), инстансы отдельно. Два
прохода: **19a** — клок GPU и память с хоста, детальный режим выкл (время кадра — отсюда); **19b** —
трассы `ovrgpuprofiler` в детальном режиме (режим, бины, стадии — отсюда, время кадра не брать).
Пол 58/58 в обоих; все 144 точки дали ровно N отрисовок; вверх и вниз расходятся в среднем на
4–9% (порог дрейфа 15%). Сырьё: `2026-09-14-quest3-run19{a,b}-*`.

**Кривая — лестница, а не излом.** 19a, GPU мед, мс, среднее вверх/вниз:

| N | 0 | 200 | 350 | 400 | 600 | 650 | 800 | 900 | 1000 | 1600 |
|---|---|---|---|---|---|---|---|---|---|---|
| off | 2.76 | 3.94 | 3.98 | **5.55** | 6.11 | **7.0** | 6.63 | **8.09** | 8.46 | 9.44 |
| 2x | 2.70 | 2.39 | 2.99 | 3.18 | 3.98 | **4.7** | 5.92 | 6.34 | **7.72** | 8.97 |

Ступени ≈1.4–1.5 мс при **неизменном клоке 456 МГц** до N=1000 — разгон их не объясняет.
Кусочно-линейная подгонка фазы K (излом «на 1000» / «на 650») описывает лестницу неверно:
вердикт «излом значим» — артефакт модели, числа наклонов из неё в бюджет не брать.

**Что показали стадии (19b).**

1. **Размер тайла: 288×448, 24 бина** на буфер глаза 1680×1760 при MSAA off; **384×256, 35 бинов**
   при 2x. Режим — **HwBinning во всех 144 точках** обоих режимов. Гипотеза «смена GMEM ↔ прямой
   режим» в диапазоне 0–1600 **опровергнута**: ни режим, ни число бинов с N не меняются. Патч
   `VK_QCOM_tile_properties` для этого не понадобился.
2. **Binning и Render растут с N плавно** (off: Binning 0.01 → 1.66 мс, Render 1.34 → 4.64 мс).
3. **Ступени — вытеснение GPU.** С ростом N в исполнениях поверхности появляется стадия
   `Preempt` ≈0.7–0.85 мс, затем двойная ≈1.3–1.4 мс; доля вытесненных растёт от 0% к 100%. Off
   вытесняется с N=100–200, 2x — с 550–600. Кто вытесняет (вероятно, композитор), прибор не видит.
4. **Почему 2x дешевле off.** Поверхность без MSAA несёт `LoadColor` ≈0.9–1.0 мс и `StoreColor`
   ≈0.88 мс; поверхность 2x — `LoadColor` 0 и `StoreColor` ≈0.30 мс. Разница ≈1.5 мс на пустой
   сцене и та же, что сдвигает начало вытеснения. Откуда загрузка цвета — **не установлено**:
   в Godot `load_color` включается только для фона `ENV_BG_KEEP`
   (`render_forward_mobile.cpp:1117`), а у прибора фон по умолчанию.

**Память MSAA 2x (19a).** `vk_devicememory` процесса: **291.7 → 547.7 МБ** ровно в момент
включения 2x (между выборками 74.8 и 75.8 с), обратно — через ≈75 с после возврата на off, а не
в момент переключения. Расчёт вложений: 2 вида × 2.96 Мпикс × 2 сэмпла × 8–12 байт ≈ 47–71 МБ.
Прирост +256 МБ = 2²⁸ одним скачком — вероятно, блок кучи драйвера; сколько из него занято
вложениями, прибор не различает. **Для бюджета памяти брать +256 МБ** — это то, что видит процесс.

**Инстансы на 90 Гц.** 19a: 0.024 мкс/инстанс, значимо (разброс 0.011); 19b: 0.020, в шуме.
Цена инстанса на два порядка ниже вызова и на границе разрешения прибора; ступеньки при N=50
прогона 10 нет (0→25: 0.002 мс).

## Компиляция конвейеров: цена и лечение (прогоны 18, 20; 2026-09-14)

Фаза W, счётчики `Performance.PIPELINE_COMPILATIONS_*`, кэш устройства очищен `pm clear`.
По одному запуску на сборку — порядок величин.

| Случай | без baker | baker |
|---|---|---|
| Новый вариант материала через `material_override`, кэш холодный | **919 / 949 мс** один кадр CPU | **889 / 892 мс** |
| То же, повтор в том же запуске | 5.5 / 4.0 мс | 5.6 / 5.0 мс |
| То же, следующий запуск (кэш на устройстве тёплый) | 6.6 мс | 5.6 мс |
| W2-A: материал на меше из `.tres`, меш инстанцирован невидимым при загрузке | **4.6 мс** | **4.7 мс** |
| W2-B: `material_override` из `.tres` без предзагрузки | **1097 мс** | **1101 мс** |
| Старт движка до `_ready`, кэш холодный / тёплый | 3119–3180 / 1476 мс | 2815–2899 / 1437 мс |

- **Секундная задержка — компиляция конвейера:** повтор в том же запуске дешевле в 160–240 раз, со
  следующего запуска её снимает кэш устройства.
- **Лечит предзагрузка, а не baker.** Документация Godot: `material_override` при загрузке не
  предкомпилируется; материал меша — да, если сцена инстанцирована хотя бы раз, даже невидимой.
  Baker даёт только промежуточный SPIR-V; финальный конвейер собирает драйвер. Baker ускорил старт
  на ~300 мс (одна пара запусков).
- **Счётчики при повторе растут снова** (surface 2, draw 1, specialization 1) — они считают запросы на
  создание конвейера, а не компиляции с нуля. Судить по цене.
- **Прежнее «+5.192 мс разогрева PSO» (прогон 10) — не компиляция:** при тёплом кэше появление 16
  объектов стоит те же ~4–6 мс, что и повтор.

рассуждением (снимок состояния между ступенями не изменился ни в одном поле).

**Подпись эффекта: фиксированная цена кадра вверх, цена примитива вниз.** Это то, что дала бы
смена решения драйвера Adreno между тайловым рендерингом через GMEM и прямым в системную память.
Гипотеза получила опору, но доказательством не стала: прямой запрос размера тайла требует
`VK_QCOM_tile_properties`, которое Godot не включает.

### Промахи по дедлайну

Прибор впервые считает не только время рендера, но и доставку кадров. На 120 Гц при 1600
объектах **32–40% кадров не укладываются в бюджет, самая длинная серия — 22 подряд**. На 72 Гц
промахов нет. Прежние выводы «бюджет удержан» строились на p95 времени рендера и этого не видели.

### Потолок частоты выше, чем говорит устройство

`xrEnumerateDisplayRefreshRatesFB` отдаёт `[72, 80, 90, 120]`. Прибор запросил **144 Гц** — и
получил их, подтверждено доставкой **144.1 к/с** (дважды, в двух прогонах). Перечисление
занижает потолок; бюджет на 144 Гц — **6.94 мс**. См. поправку в ADR-0006.

**Объяснено документацией вендора** (`docs/research/sources.md`). Meta: Quest 3 с HorizonOS ≥ 2.7
поддерживает **72–207 Гц без какой-либо настройки**, выше 207 нужен масштаб рендера и два
`setprop`; перечисление частот **неисчерпывающе по замыслу**. Это сходится со всеми тремя нашими
наблюдениями, включая отказ на 240 Гц — мы не ставили требуемые свойства.

Числа 207 и 240 — **заявление вендора, а не наше измерение**, и в бюджеты они не идут. Наше
измеренное: 144 Гц работают, 240 Гц отвергнуты.

## Числа зависят от частоты — измерено, а не предположено

Прогон 5 повторил свипы на 120 Гц. Нагрузка та же, шлем тот же, разница только в частоте:

| Метрика | 72 Гц (бюджет 13.89) | 120 Гц (бюджет 8.33) |
|---|---|---|
| Пустая сцена, GPU сред | 2.500 мс | **3.130 мс** |
| N=1600, GPU сред | 9.910 мс | **7.615 мс** |
| N=1600, GPU p95 | 10.433 мс — 75% бюджета | 7.971 мс — **96% бюджета** |
| N=1600, CPU сред | 1.725 мс | **2.045 мс** |
| Один draw call, GPU | 5.34 мкс | **2.831 мкс** |
| Один draw call, CPU | 1.04 мкс | **1.229 мкс** |
| Разогрев PSO | +3.59 мс | **+7.077 мс** |

**Стоимость draw call для GPU упала почти вдвое.** При этом база пустой сцены выросла, а CPU
замедлился. Простым «на 120 Гц GPU разогнался» это не объясняется: разгон удешевил бы и базу.

**Причина не установлена.** Кандидат: уровень фовеации на Quest 3 меняется по загрузке GPU, и при
более жёстком дедлайне рантайм мог его поднять, сократив число затеняемых пикселей. Гипотеза не
проверена и в выводы не берётся (PRACTICES §3.2).

Практическое следствие важнее причины: **числа draw call недействительны без указания частоты**.
Правило 4 ADR-0006 записывалось как предосторожность, а оказалось измеренным фактом.

**Запас на 120 Гц почти исчерпан:** p95 при 1600 объектах занимает 96% бюджета против 75% на
72 Гц. И пустая сцена с XR-вьюпортом съедает 3.130 из 8.33 мс — **38% бюджета до единого
нашего объекта**.

**Цена инстанса на 120 Гц не измерена.** Рост по свипу (0.044 мс) оказался меньше разброса
прогонов (0.072 мс) — разрешение ниже шума, и прибор доложил отказ вместо числа. На 72 Гц она
измерялась: 0.019 мкс CPU / 0.082 мкс GPU.

### Настоящий сигнал: дрейф времени кадра

При троттлинге тактовых частот та же нагрузка стала бы считаться дольше. Два прогона по 18 минут:

| 18:05 | 10.588 → 10.991 → 11.047 → 10.817 | **+4.3%** | +2.2% |

**Форма важнее числа.** По минутам второй прогон даёт не ровную линию, а горб: рост с 10.50 до
~11.12 за первые семь минут (+6%), плато до 14-й минуты, затем спад до 10.56–10.82.

```
мин  0: 10.500   мин  6: 10.910   мин 12: 11.069
мин  1: 10.785   мин  7: 11.113   мин 13: 11.066
мин  2: 10.986   мин  8: 11.010   мин 14: 11.119
мин  3: 10.009   мин  9: 11.117   мин 15: 10.557
мин  4: 10.872   мин 10: 10.945   мин 16: 10.824
мин  5: 10.896   мин 11: 11.045   мин 17: 10.641
```

Выборок 59–60 в минуту, то есть форма не артефакт неравномерности.

**Вывод: устойчивого троттлинга нет.** Есть разогрев ~6% за первые семь минут с последующей
стабилизацией — это не деградация, а выход на рабочий режим. Спад в конце прогона деградации

**Чего этот вывод НЕ покрывает** (PRACTICES §3.2): более плотную нагрузку, работу на 90 Гц (где
бюджет 11.1 мс и запас впятеро меньше) и прогоны дольше 18 минут. На 90 Гц результат может быть
совершенно другим — там ОС уже сможет сбросить частоту, и проверка по частоте перестанет быть
пустой.

**Оговорка о самой метрике.** Первая версия сравнивала последнюю четверть с первой и дала +2.2%,
горба не увидев: её вердикт зависел от того, где прогон случайно закончился (обрыв на 14-й минуте
дал бы +3.3%). Исправлено на сравнение **худшей** четверти с первой — она отвечает на вопрос
«становилось ли хуже», а не «хуже ли стало к концу». Порог 5% назначен по двум прогонам, а не
выведен из природы явления, и при +4.3% запас до него **невелик**. Проверка ни разу не краснела,
то есть её различающая способность не подтверждена (PRACTICES §2.4).

### Поправка 2026-09-14: часть дрейфа — повороты головы, а не железо

Разбор TSV обоих прогонов офлайн. Нагрузка фазы E висела **в мире** на (0, 0, −2), а не на камере,
и при повороте головы уходила из кадра. Кроме пустых выборок есть **частичные**:

| Прогон | Полных (1600 вызовов) | Частичных (60–1597) | Пустых (0) |
|---|---|---|---|
| 15:36 | 1070 | 1 | 8 |
| 18:05 | 1008 | **59** | 11 |

GPU-время частичной выборки падает вместе со счётом (604 вызова → 4.48 мс, 0 → 2.608 мс — ровно
пустая сцена). Узлы в фазе E не создаются и не удаляются, так что частичный счёт объясняет только
отсечение по пирамиде видимости. Причина прежних «пустых выборок» — та же. Проверка прежде
отсекала лишь пустые (`calls > 0`), частичные шли в четверти дрейфа.

Пересчёт по полным выборкам:

| Прогон | Четверти, GPU сред, мс (полные) | Худшая к первой | Было |
|---|---|---|---|
| 15:36 | 10.671 → 10.606 → 10.656 → 10.691 | +0.2% | +0.2% |
| 18:05 | 10.922 → 11.093 → 11.102 → 10.926 | **+1.7%** | +4.3% |

```
18:05, полные выборки, мин: 0 10.580 | 1 11.084 | 2 11.019 | 3 10.978 | 4 11.075 | 5 11.059
                             6 11.037 | 7 11.113 | 8 11.164 | 9 11.117 | 10 11.083 | 11 11.095
                            12 11.130 | 13 11.077 | 14 11.117 | 15 11.090 | 16 10.824 | 17 10.641
```

**«Горба» за семь минут нет.** Первую четверть занижали частичные выборки (их больше всего в первые
пять минут). Остаётся скачок **в первую минуту** (+4.8%), плато 10.98–11.16 до 15-й минуты и спад
в последние две минуты — он полный по счёту, то есть реальный, и **не объяснён**.

**Что это меняет.** Вывод «устойчивого троттлинга на 72 Гц не видно» стал сильнее: худшая четверть
+1.7% вместо +4.3%. Порог 5% по-прежнему назначен, и метрика по-прежнему ни разу не краснела.
Обоснование порога «+4.3% при пороге 5%» в `probe_sustained.gd` опиралось на загрязнённое число.

**Чем закрыто.** С 2026-09-14 нагрузка C–D, матрицы, K, S, W и E висит на камере
(`ProbeWindow.attach_load`), а фаза E проверяет полноту **каждой** выборки поимённо. Гейт прогнан
офлайн на этих TSV и краснеет: 9 и 70 неполных. Фаза P (цена пикселя) осталась в мире: её
покрытие считается проекцией в мировых осях.

## Что ещё выяснилось на устройстве

- **Swappy принудительно отключается под OpenXR.** В логе: `VulkanHooks detected (e.g. OpenXR):
  Force-disabling Swappy Frame Pacing.` Кадровым пейсингом в VR занимается композитор шлема.
  Для VR-пути Swappy не решает ничего. ADR-0004 **уже исправлен**: флаг `swappy=yes` оставлен,
  но обоснование переписано — он защищает не-XR сборки, а не VR.
- **`rendering_method.mobile="mobile"` обязателен.** Без платформенного оверрайда навязывается
  `forward_plus`, что на шлеме даёт `Forward Mobile` не увидеть вовсе.
- **`xr/shaders/enabled=true` обязателен в `project.godot`.** Без него обход issue #115924
  не срабатывает и Vulkan-устройство вообще не создаётся.

### Признаки по суставам (прогон 13)

Сгиб пальца = 1 − (основание→кончик) / (длина цепочки); кулак = минимальный сгиб четырёх пальцев.

| Окно, рука | min-сгиб, p95 | щипок: минимум в эпизоде |
|---|---|---|
| покой L/R | ≤ 0.02 | 110 мм |
| вращение левой кистью | ≤ 0.02 | ≥ 80 мм |
| кулак левой | 0.61–0.66 в сжатии | 15.7–18.8 мм (большой у указательного) |
| щипок правой / левой | ≤ 0.09 | **5.7–14.5 мм** (7 эпизодов) |
| тычок правой | согнутые ≈ 0.45, указательный ≈ 0.02 | 19.2 мм один раз |

- **Кулак отделяется с большим запасом.** Порог входа по min-сгибу от 0.20 до 0.55 (выход ×0.6)
  даёт ровно 3 эпизода в окне кулака и 0 во всех остальных, включая вращение кистью и тычок.
  Выбрано: вход **0.40**, выход **0.24** — середина чистого диапазона.
- **Щипок отделяется узко.** Расстояние < ≈16.5 мм **при не-кулаке** разделяет настоящие щипки
  (≤ 14.5 мм) и ближайший ложный (19.2 мм в тычке): запас ≈ 5 мм, данных — 7 эпизодов. Без
  исключения кулака щипок цепляет кулак уже с 20 мм.
- **Поза тычка по суставам не отделяется:** 1 эпизод из 3. **Касание кончиком пальца по геометрии**
  дало ровно 3 из 3 — тычок распознаётся касанием.
- Эпизоды щипка — 2 у правой и 5 у левой при просьбе «ровно 3»; сырые каналы показали те же числа

### Жесты по сигналу (прогон 14)

Надпись командует жест в заданный момент; каждый сигнал — эталонный слот (срабатывание в пределах
1.5 с + 0.6 с на реакцию). Считать самому человеку не нужно.

| Жест | Результат | Лишние вне слотов |
|---|---|---|
| **Кулак левой** | **4 из 4** | нет |
| **Щипок левой** | **9 из 9** (три повтора по 3) | нет |
| Щипок правой | 6 из 9: двойные в трёх слотах, пропусков нет | нет |
| Касание шарика правым указательным | ровно 3 | — |
| Покой, вращение левой кистью | ни одного срабатывания | — |

- **Двойные щипки правой — выбросы трекинга, а не порог.** Внутри щипка расстояние кончиков на
  **один кадр** прыгает до 31–35 мм (например, 21 → 35 → 9 мм) и пересекает выход 30 мм. Три
  двойных из четырёх — такие выбросы; четвёртое — настоящее размыкание до 53 мм на 0.6 с.
- **Лечение измерено офлайн**: отпускание засчитывается через **35 мс** (3 кадра на 90 Гц). По логам
  прогонов 13 и 14 это убирает все три выброса и не меняет ни одного другого срабатывания, включая
  окна покоя и вращения. **Подтверждено на шлеме прогоном 15** (ниже).

### Ладонь к лицу / от лица (прогон 14)

- **Признак `palm_head` (нормаль по векторам суставов) рабочий.** На 11 тысячах кадров левой руки
  при `palm_head < −0.5` флаг рантайма `menu_gesture` (ладонь к лицу) не загорелся **ни разу**
  (0 из 4793), при `> +0.5` горит в 74%.
- Правая рука разделяется напрямую: к лицу медиана +0.99, от лица −0.94 и −0.59.
- **Левая «не разделилась» потому, что поза не менялась:** в слотах «от лица» 1 и 3 рантайм тоже
  видел ладонь к лицу (178 и 225 кадров из 225). Команда «от лица» для левой руки неоднозначна;
  подсказка заменена на «ладонь от себя, вперёд».
- **Это же объясняет прогон 13:** в естественной позе щипка ладонь смотрит к лицу — отсюда и +0.99
  в окнах щипка, и ложные `menu_pressed` на обычном щипке левой.
- **Ось Y сустава ладони нормалью не является:** за 11 тысяч кадров ни разу не превысила +0.5.

## Что НЕ измерено

- **Экономия от MSAA с `LAZILY_ALLOCATED`.** Godot её не задействует (TODO в
  `render_scene_buffers_rd.cpp:188`). Цена MSAA без неё **измерена** прогоном 10 — и она
  отрицательная; см. раздел про ручки рендера.
- ~~Стоимость отрисовки под MSAA 2x~~ — **измерена** прогоном 11 лестницей; оси пикселей под 2x
  нет.
- ~~Форма лестницы вызовов~~ — **измерена** прогоном 19: ступени ≈1.4 мс от вытеснения GPU
  (`Preempt`), а не смена режима. **Кто вытесняет** — не установлено.
- ~~Механизм удешевления от MSAA~~ — **найден** прогоном 19: `LoadColor` + `StoreColor` ≈1.9 мс на
  поверхности off против 0.3 мс у 2x. **Откуда загрузка цвета** при фоне по умолчанию — не установлено.
- ~~Затраты памяти на MSAA-буферы~~ — **+256 МБ** процесса (прогон 19); доля собственно вложений
  внутри блока не различена.
- ~~Реальный размер тайла~~ — **288×448 (off), 384×256 (2x)**, `ovrgpuprofiler`, прогон 19.
- **Работа на 80 Гц.** Прогоны есть на 72, 90 и 120; 80 Гц не пробовались. Целью не является.
- **Дрейф за прогон не объяснён.** Канарейка даёт +4.6% на 72 Гц и +13.1% на 90 за сто секунд,
  база пустой сцены ползёт вверх. Прогрев это или что-то ещё — не установлено; на 120 Гц фаза E
  не прогонялась, а на 90 длинного прогона тоже не было.
- **Дрейф на 120 Гц.** Канарейка прогона 6 показала +49.9% между двумя ступенями 120 Гц против
  +4.2% между ступенями 72 Гц. Что это — прогрев, накопленное состояние драйвера или дефект
  самой канарейки, — не установлено. Канарейка с 2026-09-13 пишется в TSV матрицы с unix-временем
  и сводится с клоком (`tools/join_windows.py`); прогона на 120 Гц с этим пока не было.
- ~~Троттлинг на целевой частоте~~ — **прогнан** (прогон 24): 18 минут на 90 Гц при N=800, дрейфа нет,
  клок на 456 МГц. **Открыто:** температура к концу не вышла на плато (46 °C), плотная нагрузка и
  прогоны дольше 18 минут не мерились.
- **Троттлинг на 120 Гц.** Фаза E на 120 Гц НЕ прогонялась: прогон 5 шёл с маркером
  `skip_sustained`. Все выводы о термальном поведении относятся к 72 Гц, где кадров в секунду
  в 1.67 раза меньше. На 120 Гц слежение за сменой частоты впервые перестало быть пустым —
  сбрасывать есть куда.
- **Почему цена draw call падает на 120 Гц сильнее, чем объясняет клок.** Прогон 9 сузил
  вопрос: в рабочем диапазоне 72–90 Гц остаток после нормировки на клок равен 1.047, то есть
  эффект там **исчерпывается разгоном**. Необъяснённые ≈1.5 остаются только у пары 72↔120, как и
  подорожание пустого кадра при равном клоке. Ось пикселей закрыла пиксельные версии: цена
  пикселя от частоты не зависит (0.98 и 1.04 в двух прогонах). Ведущая гипотеза — смена режима
  GMEM/прямой рендеринг у драйвера Adreno; проверить её прямо мешает отсутствие
  `VK_QCOM_tile_properties` в сборке Godot. **Для проекта вопрос перестал быть блокирующим:**

- ~~Цена пикселя~~ — **измерена** прогонами 8 и 9: 117–140 мкс на затеняемый мегапиксель,
